# Novel Tracker 账号与云同步设计

日期：2026-10-10

## 目标与边界

读者可以继续不登录地使用本地书库。登录同一账号后，iPhone 与 Android 设备自动同步小说、阅读记录、摘记、标签、封面和摘记图片；断网时可以继续编辑，联网后续传。OCR 识别文本是设备缓存，下载图片后由本机重新建立，不上传到云端。第一版只支持邮箱验证码登录，不做公开主页、社交关系、付费或网页端。

## 账号与本地资料

使用 Supabase Auth 的邮箱验证码。原有 `novel-tracker.db` 始终是未登录书库。每个账号使用按 Auth 用户 UUID 命名的独立 SQLite 文件和图片目录；退出账号立即切回未登录书库，不能在另一个账号的页面看到上一账号的数据。账号本地缓存保留，方便同账号再次登录。首次登录时若未登录书库非空，明确询问是否把这些记录加入账号；不自动清空或移动原始书库。重复登录不会重复导入同一批记录。

## 云端与权限

Supabase Postgres 保存账号当前书库清单、单调递增的版本号和更新时间。私有 Storage bucket 保存按 `用户 UUID/图片 UUID.扩展名` 命名的图片。所有表启用 RLS，只有 `auth.uid() = user_id` 可读写；Storage policy 限制用户只能访问自己目录。客户端只放 publishable key，不放 service role key。数据库 RPC 以预期版本号做原子写入，防止两台设备覆盖同一版本。SQL 迁移及部署步骤随代码提供；未配置 Supabase 时入口显示“云同步尚未配置”，本地功能保持可用。

## 同步协议

本机 SQLite 是离线读写源。首次登录拉取云端清单，和本机账号书库做初始合并。成功同步后保存一份基线清单及云端版本。每次同步分别比较本机、基线和云端：仅本机变更的记录上传，仅云端变更的记录下载，两边各自新增的记录合并。书籍、阅读记录、摘记、标签和图片按稳定 ID 比较；同一实体两边都改动、或一边删除另一边修改时，暂停该轮写入并向用户展示冲突，保留两份内容供选择。相关联的集合在合并后必须通过现有备份验证；验证失败也按冲突处理。不能静默以“最后写入者获胜”覆盖内容。

上传新图片先于发布引用它的云端清单。拉取时将缺少的图片下载到账号目录，验证长度和可解码性，然后在本地事务中应用清单。若上传、下载或数据库写入失败，保留本机数据和上一次同步基线，显示可重试状态。同步过程中若本机又有修改，则放弃本次本地覆盖并重新合并。远端图片删除延迟清理，以免另一台离线设备引用仍在使用的图片。

App 启动、回到前台、登录成功时触发同步；前台每 15 秒检查本机及远端变更，用户也可手动同步。重复触发合并为单个同步任务，不并发上传。页面显示“已同步／正在同步／等待重试／需要处理冲突／同步失败”，并提供手动重试。退出账号停止后续同步任务。

## 用户流程与安全

管理页增加“账号与同步”。页面提供输入邮箱、发送验证码、验证、当前账号、同步状态、重试、退出账号和删除账号。邮箱仅用于登录；验证码错误、过期、网络失败使用明确提示，不清除本地记录。登录前说明书库和图片会上传到所选云服务。首次登录时访客书库与账号书库分开；访客书库若非空，用户可明确选择复制导入。冲突界面按记录展示本机与云端内容，用户选择其中一份后再继续同步；未选择的版本不会自动保留，因此界面会要求先分别备份两台设备。

删除账号需二次确认，并通过受保护的服务端函数删除该用户的云端清单、图片及 Auth 账号；本地账号缓存随后清除，未登录书库不受影响。删除流程失败时不能提示完成，也不能先抹掉唯一的本地资料。用户仍可从现有“备份与恢复”导出独立备份。

## 验收

两台模拟设备使用同一账号：A 新增书、B 新增另一书后自动同时出现；断网编辑后恢复网络同步；封面及摘记图片在第二台可打开；同一条摘记被两台修改时不静默覆盖；退出后无法看到账号书库；另一账号不能读该账号清单或图片；同步失败可重试且本地书库未损坏。测试覆盖合并、删除冲突、账号隔离、版本竞争、图片缺失和上传失败。最终真机验收须使用已配置的 Supabase 项目，验证邮箱投递与两台设备实际传输。
